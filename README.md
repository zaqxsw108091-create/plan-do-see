# 플랜두씨 다이어리 (Plan · Do · See)

계획을 세우고(Plan), 실제로 한 일을 시간과 함께 기록하고(Do), 계획 대비 결과를 돌아본 뒤 고칠 점을 다음 계획으로 넘기는(See) 개인 다이어리 웹앱입니다.

## 해결하려는 문제

할 일 앱은 "했다/안 했다"만 남깁니다. 그래서 **계획한 시간과 실제 걸린 시간이 얼마나 달랐는지**, **어디서 막혔는지**가 남지 않고, 다음 계획도 같은 방식으로 틀립니다.
이 앱은 계획 → 할 일 → 실행 기록 → 돌아보기 → 다음 계획을 하나로 잇습니다. 내 계획이 어느 쪽으로 자주 틀리는지 숫자와 근거 기록으로 보여줍니다.

## 기능

| 탭 | 기능 |
|---|---|
| 계획 | 기간·우선순위·성공 기준·예상 시간. **최초 계획은 바꾸지 않고 보존**하고, 수정하면 이전 값이 수정 이력에 쌓임. 지난 돌아보기의 고칠 점을 새 계획에 붙임 |
| 할 일 | 계획에 딸린 할 일 추가·수정·완료·되돌리기·삭제. 마감일·우선순위·태그·예상 시간(분). 검색·거르기·정렬, **정렬 기준을 화면에 표시** |
| 실행 기록 | 시작·끝 시각, 실제 걸린 시간, 막힌 이유를 계획과 **별도 표에** 저장. 입력 검증, 기록 수정·삭제. **완료를 연타해도 1건만** 기록 |
| 돌아보기 | 계획별 계획한 할 일 / 완료 / 지연 / 막힘 / 예상 대비 실제 시간. **숫자를 누르면 그 숫자를 만든 기록이 펼쳐짐**. 고칠 점 한 줄을 다음 계획으로 넘김 |
| 내보내기 | 전체 데이터를 JSON 파일 하나로 저장 |

## 기술적으로 고민한 점

**1. 결과물과 소스를 같은 곳에서 → 정적 호스팅 + 외부 DB**
- 문제: GitHub Pages는 정적 파일만 올릴 수 있어서, 입력한 데이터를 저장할 곳이 없습니다.
- 선택: 화면은 GitHub Pages, 데이터는 Firebase Firestore(무료 요금제, 서울 리전)에 저장합니다.
- 버린 대안: localStorage는 다른 컴퓨터에서 보이지 않아 평가자가 내 기록을 볼 수 없습니다. 서버를 따로 두면 비용과 관리할 것이 늘어납니다.

**2. 완료 중복 방지 → 버튼 잠금만 믿지 않기**
- 문제: 버튼만 잠그면 다른 탭이나 다른 컴퓨터에서 누를 때, 또는 네트워크 재시도가 일어날 때 기록이 두 번 쌓입니다.
- 해결:
  - ① 서버 트랜잭션에서 할 일을 다시 읽어 이미 완료면 기록하지 않습니다.
  - ② 실행 기록 id를 요청 키로 한 번만 만들어, 재시도해도 같은 문서에 씁니다.
  - ③ 완료/되돌리기 버튼은 토글이 아니라 목표 상태를 보냅니다.
  - ④ 저장 직후 0.6초는 입력을 받지 않습니다.
- 실제로 잡은 버그: 빠른 더블클릭의 두 번째 클릭이 새로 그려진 "되돌리기" 버튼에 눌려 완료가 도로 풀렸습니다. ③과 ④로 막았습니다.

**3. 입력 실수가 집계를 망가뜨리는 문제 → 입력 구조로 원천 차단**
- 문제: 막힌 게 없던 기록에 이유로 "없음"이라고 적었는데, 돌아보기에서 막힘 1건으로 집계됐습니다. 게다가 잘못 적은 기록을 고칠 방법이 없었습니다.
- 해결: "없음"이라는 단어를 예외 처리하는 대신, **"막힌 점이 있었음"을 체크해야 이유 칸이 열리도록** 바꿨습니다. 실행 기록 수정·삭제도 추가했습니다.

**4. 시간대 → 저장은 숫자, 입력·표시는 항상 한국 시간**
- 문제: 입력칸은 사용하는 컴퓨터의 시간대로 해석됩니다. 그래서 한국이 아닌 곳에서 열면 같은 시각이 다르게 저장됩니다.
- 해결: 입력값을 항상 한국 시간(UTC+9)으로 해석하고 한국 시간으로 표시합니다. 지연 판정의 "오늘"도 한국 날짜입니다.

## 파일 구성

| 파일 | 역할 |
|---|---|
| `index.html` | 과제 6 앱 (로그인 없음, 화면 + 로직, 빌드 없음) |
| `private.html` | 과제 7 앱 (Firebase 로그인 + 계정별 저장 공간, 다크모드·달력·5일 관찰 탭) |
| `contracts/pds-schema-v2.json` | 데이터 계약 (표·항목·관계·날짜 규칙) |
| `firestore.rules` | Firestore 보안 규칙 |
| `migrate.html`, `plan-do-see.html` | 예전 버전 자리. 열면 바로 앱(`index.html`)으로 이동하며 기능 없음 |

**실행 방법:** 빌드가 필요 없습니다. 결과물 주소로 접속하면 됩니다. 로컬에서 볼 때는 저장소 폴더에서 `python -m http.server 8000`을 실행한 뒤 http://localhost:8000 에 접속합니다.

**기술 스택:** HTML / CSS / Vanilla JavaScript (ES Modules), Firebase Cloud Firestore, GitHub Pages

## 보안 점검

- **스크립트 삽입:** 사용자가 입력한 모든 글자는 화면에 넣기 전에 HTML 이스케이프합니다(C57 테스트 통과).
- **비밀값:** 코드·저장소에 비밀키·비밀번호·토큰이 없습니다.
  - `firebaseConfig`의 `apiKey`는 Firebase가 웹 공개를 전제로 발급하는 **프로젝트 식별값**이고, 비밀키가 아닙니다.
  - 데이터 접근 권한은 `firestore.rules`가 정합니다.
- **공개 범위:** 과제 조건상 로그인이 없어서, 링크를 아는 사람은 누구나 데이터를 읽고 수정·삭제할 수 있습니다. 대비로 "내보내기"로 백업을 남깁니다.

## 한계와 다음 개선

- 과제 6 버전(`index.html`)은 로그인·사용자별 권한이 없습니다. 인증과 사용자별 보안 규칙은 과제 7 버전(`private.html`)에 붙였습니다.
- 실행 기록을 삭제해도 할 일의 완료 상태는 자동으로 되돌리지 않습니다(의도한 동작). 필요하면 "되돌리기"를 누릅니다.
- 계획 자체의 삭제 기능은 없습니다. 지나간 계획도 돌아보기 근거로 남겨두려는 의도입니다.

## AI 활용 방식

- **AI에게 맡긴 일:** 화면·저장 코드 작성, Firebase 연동, 과제 기준별 자동 테스트 작성
- **내가 직접 판단한 일:**
  - 결과물과 소스를 GitHub에 함께 두기로 하고 Firebase로 전환한 결정
  - 실제로 쓰다가 "없음" 입력이 막힘으로 잡히는 문제를 발견한 것
  - 업그레이드 우선순위를 정한 것
- **AI 제안을 따르지 않은 일:**
  - "결과물과 소스는 따로 둬도 된다"는 AI 의견 대신, 이전 과제 방식대로 GitHub 한 곳에 두었습니다.
  - AI가 제안한 "기록 생성 시각을 직접 입력하는 칸"은 쓰지 않았습니다. 기록 시각을 사용자가 바꿀 수 있으면 데이터 신뢰도가 떨어지기 때문입니다.
